# Product Context

> Только то, что влияет на решения агента. Термины — в `domain-glossary.md`.

## Что за продукт

Сервис «Кадровые комиссии» (КК) для HR-функции. На кадровой комиссии по каждому оцениваемому сотруднику решают, по какому карьерному треку он пойдёт: ротация, развитие в роли, развитие вне компании и т. п.

Сейчас процесс ведут вручную две команды: Excel, бумага, почта. Владелец процесса не видит, на каком этапе каждое подразделение. Каждый год КК собирают заново. Связки «HRD ↔ подразделение» в Пульсе нет.

**MVP** — подготовка альфа-КК в одном сервисе: от создания комиссии до согласования владельцем проектов решений по всем подразделениям. Сама встреча и всё, что после неё, — за границей MVP. Модель при этом не должна мешать GAMMA: механика задаётся типом КК.

Пилот заодно проверяет модель маленькой команды и spec-driven development на OpenSpec. Отсюда требования к артефактам: единый язык в речи, макетах и коде, понятные и воспроизводимые спецификации.

## Пользователи и роли

| Роль | Что делает |
| --- | --- |
| Владелец процесса | Около пяти человек из команд поддержки процесса КК и работы с ТОП-600. Создаёт и копирует КК, видит и правит все КК, согласует заявки и подразделения, ведёт шаблоны проектов решений |
| Владелец комиссии | Сотрудник с доступом к конкретной КК. Внутри неё может всё, что владелец процесса, кроме создания и копирования |
| HRD | Курирует до трёх подразделений. В ALPHA заполняет проекты решений, подаёт заявки на изменение состава, отправляет подразделение на согласование, выдаёт доступ делегатам |
| Делегат HRD | Подчинённый HRD с теми же правами в выданном подразделении. Передать доступ дальше не может |
| Руководитель подразделения | Смотрит и правит проекты решений своего подразделения, ничего не согласует |
| Роль поддержки | Ведёт справочники владельцев процесса и HRD |

Оцениваемые доступа к сервису не получают. Председатель, эксперты и приглашённые — роли встречи, они вне MVP.

## Ключевые сценарии

1. **Подготовить черновик КК.** Владелец процесса задаёт параметры проведения (название, регламент, тип, грейды, подразделения), этапы, оцениваемых с причиной рассмотрения и шаблон проектов решений. Изменения сохраняются автоматически, к черновику можно вернуться. Вместо создания с нуля можно сделать «Создать на основе» прошлой КК.
2. **Запустить КК.** «Создать» проверяет заполненность. Активация фиксирует снимок подразделений с руководителями и HRD и ставит HRD задачи в Пульсе.
3. **Заполнить проекты решений.** HRD или делегат заполняет проект решения по каждому оцениваемому своего подразделения и отправляет подразделение на согласование. Руководитель может поправить проект.
4. **Изменить состав.** HRD подаёт заявку на добавление или исключение одного человека с обоснованием. Владелец согласует или отклоняет её.
5. **Проконтролировать и согласовать.** Владелец видит статус каждого подразделения и согласует их. Когда согласованы все подразделения, MVP по этой КК пройден.
6. **Настроить шаблоны проектов решений.** Варианты решений и поля контекста — общий ресурс владельцев процесса. Через них фокус КК меняется год к году без доработки системы.
7. **Раздать доступ.** Владелец процесса назначает владельцев комиссии, HRD — своих делегатов.

## Что нельзя ломать

- **Персданные не хранятся.** Люди везде записаны как `person_id` (UUID из `PersonProfile`), ФИО запрашиваются при показе.
- **Снимок при активации.** Подразделения, руководители, HRD и привязка оцениваемых фиксируются в момент «Создать» и потом с оргструктурой не синхронизируются. Грейд, звено и стаж, наоборот, берутся при каждом показе.
- **Параметры проведения меняются только в `DRAFT`.** Инварианты проверяет агрегат `PersonnelCommission`, а не контроллер.
- **Пустых КК нет.** КК появляется при первом изменении формы, id присваивает сервер.
- **Состав в активной КК меняется только через согласованную заявку.** HRD не меняет состав без владельца. Каждый человек попадает в КК не больше одного раза.
- **Используемый шаблон не меняется и не удаляется.** Это шаблон, привязанный хотя бы к одной КК вне черновика.
- **Доступ строго по роли и структуре.** Данные оцениваемых конфиденциальны: грейды, оценки. Делегат HRD не передаёт доступ дальше.
- **Аудит.** В каждой таблице есть суррогатный `id` и поля `created_at`, `created_by`, `updated_at`, `updated_by`. Они заполняются автоматически.
- **Единый язык.** Имена в коде и API — из `domain-glossary.md`. Запрещены «блок», «Данные КК», `CommissionData`, `DepartmentEditor`.

## Known limitations

- **Внешних API пока нет:** `OrgStructure`, `PersonProfile`, система грейдов, задачи и уведомления Пульса. Порты и их контракты формулируем сами. Фейки работают в тестах и в dev-профиле, реальные адаптеры появятся отдельными задачками.
- **Связка «HRD ↔ подразделение»** ведётся справочником `hrd_assignment` и читается через `HrdResolver`. Позже HRD может вычисляться по структуре.
- **Справочники** до появления API для роли поддержки наполняются миграцией.
- **Активируется только ALPHA.** Механики GAMMA и BETA не описаны.
- **Истории изменений (`change_log`) нет.** Есть только аудит-поля и история статусов. Исключённый оцениваемый удаляется вместе с проектом решения, след остаётся только в заявке.
- **Одновременные правки черновика** — побеждает последняя запись, оптимистической блокировки нет.
- **Защиты от повторного создания нет.** Если связь оборвётся на первом сохранении черновика, может появиться дубль. Его удаляют вручную.
- **Только бэкенд.** UI делается отдельно по фрагменту OpenAPI, который фиксируется в proposal.
- **Не решено:**
  - как КК переходит в `COMPLETED`;
  - как показывать карточку оцениваемого (блокирует фазу B);
  - правят ли шаблоны владельцы комиссии;
  - можно ли снять подразделение, в котором есть оцениваемые (пока нельзя);
  - кому показывать историю изменений;
  - права председателя.
